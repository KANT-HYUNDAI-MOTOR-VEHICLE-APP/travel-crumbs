## 1. 요약 (수정: 2026-11-05 서버 사용 팀 결정 반영) (수정: 2026-11-06 A-14 실패 폴백) (수정: 2026-11-07 A-14 전용 화면)

## 3. 상태

### 3.1 홈 UiState 에 더하는 칸 (수정: 2026-11-05 #6 답변 반영) (수정: 2026-11-06 A-14 실패 폴백 — `routeRequest` 실패에 장소 · `dummyRoute` · 행동 셋) (수정: 2026-11-07 A-14 전용 화면 — `guideScreen` · `dummyRoute` 자리 · 「길안내 화면 닫기」)

기존 칸(`drivingState` · `naviReady` · `navi` · `openedByGleoAction`)은 #6 이 홈을 다시 짤 때의 칸을 따름 — `drivingState` 는 #6 의 합성 판정 값(결정 기록 U37).

| 칸 | 뜻 | 처음 값 |
|---|---|---|
| `pinnedPlaces` | 「가 볼 장소」에 그릴 고정 장소 목록(고정 순서 · 장소마다 id · 이름 · 주소) · 기기 저장을 아직 못 읽었으면 「읽기 전」 — 좌표는 화면 상태에 넣지 않음(화면이 그리지 않으므로) | 읽기 전 |
| `candidates` | 「장소 고르기」에 그릴 후보 목록(후보 JSON 순서 · 장소마다 id · 이름 · 주소 · 고정 여부) | 후보 전부 · 고정 여부는 고정 목록을 읽은 뒤 채움 |
| `placesVisible` | 「가 볼 장소」 · 「장소 고르기」 두 구역을 그리나 — `drivingState` 가 PARKED 일 때만 참(바뀌기 전 `pickerVisible` 을 넓힘) | 거짓 |
| `canPinMore` | 고정 수 < 최대(결정 기록 U16) — 거짓이면 E8 표시 · 「고정」 비활성 | 참 |
| `routeRequest` | 마지막 길안내 요청 상태 — 대기 · 요청 중(장소 id) · 시작됨(장소 이름) · 실패(이유 코드 · 장소 id) — 실패의 장소 id 는 「다시 시도」 · 「더미 경로」의 대상(요청할 때의 장소 · 그 뒤 고정 해제해도 그대로) · 표준 코드 대응은 4.1 | 대기 |
| `guideScreen` | (2026-11-07) 길안내 연결 화면(2.3)을 그리나 — 닫힘 / 열림(장소 id · 이름 · 주소) · 좌표 · 현재 위치 칸 없음 · 「여기로 안내」로 요청을 시작한 때 열림(U68) · 닫히는 때는 2.3 「열림 · 닫힘」 표 · 열림이면 홈 목록(두 구역 · 맨 위 영역 · debug 카드)을 그리지 않음 | 닫힘 |
| `dummyRoute` | 더미 경로 모드(2.3 G1-D · 옛 E13)를 켜나 — 없음 / 장소(id · 이름 · 주소) · 좌표 · 현재 위치 칸 없음(화면이 그리지 않으므로) · `routeRequest` 가 실패 · `guideScreen` 이 열림이고 사용자가 「더미 경로」를 눌렀을 때만 「장소」 · debug 빌드가 아니면 늘 없음(U55) · `guideScreen` 이 닫히면 함께 없음 | 없음 |

- 바뀌기 전의 `places`(고정 값 전부) 칸은 `pinnedPlaces` · `candidates` 로 나뉨.
- 「여기로 안내」 버튼 활성 여부는 따로 칸을 두지 않고 `naviReady` · `routeRequest` 에서 정함 — 활성 = `naviReady` 이고 `routeRequest` 가 요청 중이 아님(구역은 `placesVisible` 일 때만 그려짐).
- 「다시 시도」 · 「더미 경로」도 따로 칸을 두지 않음 — 보임 = `guideScreen` 열림 · `routeRequest` 가 실패(「더미 경로」는 debug 빌드만) · 「다시 시도」 활성 = 「여기로 안내」 활성과 같은 식 · 「더미 경로」 활성 = `dummyRoute` 가 없음.
- 실패 이유 코드(앱 안 값 · 4.2): `NOT_CONNECTED` · `TOO_CLOSE` · `TOO_FAR` · `LOW_BATTERY` · `ROUTE_NOT_FOUND` · `TIMEOUT` · `REQUEST_FAILED`.
- 사용자 행동은 ViewModel 메서드 — 「여기로 안내」(장소 id) · 「고정」(장소 id) · 「고정 해제」(장소 id) · 「다시 시도」 · 「더미 경로」(둘은 인자 없음 — 대상은 `routeRequest` 실패의 장소) · (2026-11-07) 「길안내 화면 닫기」(인자 없음 · G6 「닫기」와 시스템 뒤로가 같은 메서드). 옛 「더미 경로 닫기」는 없앰 — 더미 경로 모드는 화면을 닫을 때 함께 꺼짐. 모두 `drivingState` 가 PARKED 가 아니면 무시 · 「다시 시도」 · 「더미 경로」는 `routeRequest` 가 실패가 아니면 무시. 결과는 이벤트가 아니라 상태 칸으로(android-architecture 규칙 5).
- `guideScreen` · `dummyRoute` 는 기기 저장 · `SavedStateHandle` 복원 대상 아님 — `routeRequest` 와 같이 일회성(프로세스 재생성 뒤 없음).
- 고정 목록의 단일 출처는 기기 저장을 감싼 저장소 — ViewModel 은 그 흐름을 받아 `pinnedPlaces` · `candidates` · `canPinMore` 를 만듦(화면에서 따로 들고 있지 않음).

- 후보 장소 자리: **앱 안 한 곳 · 쉽게 바꿀 수 있는 자리**(android-architecture 규칙 6 의 콘텐츠 자리) — `app/src/main/assets/` 의 JSON 파일 하나(결정 기록 U3). 화면 · ViewModel 은 저장소를 거쳐 받음(규칙 4). 고를 원본이 생기면(#3 방문 기록 · 다른 사람의 여행지 · 공유받은 여행) 후보 저장소의 자료원만 바꿈 — 그때 id 체계가 달라 기존 고정이 보이지 않을 수 있음(시연용이라 받아들임 · 2.1 「후보에 없는 id」 규칙으로 처리).
- 여행 안 순서: 지금은 여행 시작 · 종료가 없어(#6 D2 — 첫 실행부터 기록 중 · 여행 구분은 route · #3 기획 뒤) 내 핀 전체를 한 여행으로 보고 기록된 차례대로 1, 2, 3 … · 같은 장소를 다시 가면 새 핀(순서 다음 번호). #3 이 여행을 나누면 순서도 여행별.
- 고정 목록 · 핀 · 장소별 안내 건수는 각각 저장소 하나를 거침(규칙 4) · 고정 목록 = DataStore(결정 기록 U20) · 핀 저장 방식은 U43.
- **핀(기기 원본)과 서버 보냄의 관계**: 핀 1건 = 보낼 기록 1건. 보냄 상태만 바뀌고 핀은 남음 — 대기(아직 못 보냄 · 다시 보낼 대상) → 끝(201 · 200) 또는 거절(422 · 다시 보내지 않음). 재시도 대기열 = 보냄 상태가 「대기」인 핀들(따로 지우는 큐 없음 · 결정 기록 U46 · U29 의 「보내면 지움」을 대신함).
- **저장소 경계(요구)**
  - 핀 저장소: 「핀 남기기」 · 「현재 여행의 핀을 순서대로 읽기」 · 「대기 핀을 서버로 보내기」. 핀을 실제 여행(trip)에 붙이는 일은 #3 이 이 저장소의 구현을 바꿔 끼워서 함 — 화면 · ViewModel · 도메인은 고치지 않아도 되게.
  - 건수 조회 저장소: 「장소별 안내 건수 조회」 — 서버 구현.
  - 서버 호출 쪽 · 핀 저장소를 시험용 fake 로 바꿔 끼울 수 있어야 함(실패 · 재시도 · 여행 붙이기 · 서버 없는 개발 시험). 서버가 없을 때의 시연 폴백은 두지 않음 — fake 는 시험에만(U47 추천 기준).
- 서버 호출은 Retrofit 인터페이스(`data/remote/AppApi`) 하나 · 계약(5절)과 경로 · 메서드 1:1(`POST /navigation-starts` · `GET /navigation-starts/stats`) · 요청 DTO 는 `placeId` · `startedAt` 두 칸만(좌표 · userId 칸 없음 · android-architecture 규칙 8) · 주소는 기존 `BuildConfig.API_BASE_URL`(debug `http://10.0.2.2:4000/`) · 토큰을 붙이는 일(AuthInterceptor · TokenAuthenticator)은 #1 — #1 전엔 debug 빌드 전용 시드 토큰(결정 기록 U27).
- 기기 저장은 백업 대상 아님 — 매니페스트 `allowBackup="false"` 유지.
- 내비에 넘기는 값: 위도 · 경도 · 장소 이름 · 주소. POI 식별자(poiId · poiSubId)는 빈 문자열 — 우리 장소엔 POI 가 없음 · SDK 칸이 null 을 받지 않음 · 빈 채로 안내 시작됨(2026-11-06 에뮬레이터 · 5곳 모두 · 내비 로그 경고 한 줄 · 내비의 최근 목적지 기록만 건너뜀)(결정 기록 U6). 경로 옵션은 지정하지 않음 — 내비 기본값 · 운전자 설정을 따름(결정 기록 U12).
- 이미 안내 중일 때 새 요청 = 목적지 바꾸기(Pleos 문서: `requestRoute` 는 목적지 설정 · 변경 · 재설정에 씀). 장소 여러 곳을 잇는 안내 · 진행 중 경로에 장소 더하기 · 전체 코스 재안내는 만들지 않음(데이터 표준 v0.3 용어 — 순서 있는 장소 목록은 모두 장소 구조).

길안내 요청 상태 코드(데이터 표준 v0.3 R10 · 코드 그룹 `NAVI_REQ_STATUS`)

- 표준 R10 「앱 로직과 연결된 상태 코드는 앱 상수로도 정의」 → 앱 domain 에 `NAVI_REQ_STATUS` 의 세 값 `REQUESTING` · `SUCCESS` · `FAILED` 를 한 곳에 상수로 둠(android-architecture 규칙 6 · 같은 값 두 곳 금지) · 이름은 표준 코드값(가안) 글자 그대로 · 코드값 형식(M01 — 영문 대문자 · 숫자)이 바뀌면 그 한 곳만 고침(U59).
- 화면 상태 `routeRequest`(3.1)와의 대응 — 화면 상태는 「대기」를 더 가짐(요청이 없는 때 · 사건이 아니라 코드 없음).

| `routeRequest`(화면 상태 · 3.1) | `NAVI_REQ_STATUS` | 비고 |
|---|---|---|
| 대기 | 없음 | 요청 전 · 프로세스 재생성 뒤 |
| 요청 중(X) | `REQUESTING` | 표준 「NaviHelper 호출 후 결과 대기」 · 「다시 시도」도 새 `REQUESTING` |
| 시작됨(X) | `SUCCESS` | 표준 「차량 길안내 시작됨」 = `onRouteStarted` 또는 대조(결정 기록 U4 넓힘) |
| 실패(이유 · X) | `FAILED` | 표준 「호출 실패(더미 경로 폴백)」 — 「다시 시도」 · 「더미 경로」는 이 상태에서만. 실패 이유 코드(4.2)는 앱 안 값 · 표준 코드 그룹 아님 · 서버로 가지 않음 |

- 표준 전이는 `REQUESTING → SUCCESS / FAILED` 뿐 — 이 스펙의 「실패(`TIMEOUT`) 뒤 늦은 시작 판정 → 시작됨」(3.2)은 `FAILED → SUCCESS` 로 표준 전이 밖. 화면 상태로는 그대로 둠(실제로 안내가 시작됐으므로) · 사건 기록(`navi_req_log` · 추가만)을 만들 때 한 요청에 `FAILED` 뒤 `SUCCESS` 행을 더하는지가 정할 일(U58).
- `navi_req_log`(길안내요청로그 · ERD v0.3 · 로그 유형 · 추가만)는 **이번엔 만들지 않음** — 기기 · 서버 어디에 둘지가 팀 미결(M09 · U58). 지금 안내 시작 사건은 핀(기기) · `navigation_starts`(서버 · 5절)에만 남음 · 실패 · 더미 경로 사건은 어디에도 남지 않음.

더미 경로 · 길안내 연결 화면(2.3)의 데이터 (2026-11-07 — 옛 E13 의 값을 2.3 지도 박스로 옮김)

- 2.3 지도 박스(G1)가 그리는 값 = 요청한 장소의 이름 · 주소(후보 고정 값에서 id 로 찾음) + 고정 글자 「목적지」 · 「현재 위치」 — 요청 중 · 시작됨 · 실패 모두 · release 에도. 더미 경로 모드(G1-D)는 여기에 고정 모양 선 · 시연용 표시만 더함. `guideScreen`(3.1)은 화면 상태뿐 · 새 모델 · 저장 · 서버 칸 없음.

- 그리는 값 = 실패한 장소의 이름 · 주소(후보 고정 값에서 id 로 찾음 · 2.1 「가 볼 장소」와 같은 길) + 고정 글자 「현재 위치」. 좌표 · 현재 위치 · 거리 · 경로 모양은 읽지도 만들지도 않음(U53 추천 기준).
- 새 모델 · 저장 · 서버 칸 없음 — `dummyRoute`(3.1)는 화면 상태뿐 · 핀 · 고정 목록 · 서버 보냄 · 로그에 영향 없음(U56 추천 기준).

### 4.2 내비 오류 → 실패 이유 (수정: 2026-11-06 구현 · 실측 반영)

내비 오류 코드는 Pleos 문서 「목적지 설정」에 값 목록이 없어, 저장소가 쓰는 SDK(navi-data 3.0.4)의 `NaviErrorCode` 값 이름을 근거로 함. 값의 뜻 설명은 문서에 없어 값 이름에서 읽은 뜻으로 아래 표대로 확정 · 표에 없는 값은 일반 문구로 떨어짐(결정 기록 U5).

| 내비 오류 코드 | 실패 이유 코드 | E3 이유 문구 |
|---|---|---|
| `CAUSE_SEARCH_ROUTE_TOO_SHORT_DISTANCE` | `TOO_CLOSE` | 「너무 가까운 곳이에요」 |
| `CAUSE_SEARCH_ROUTE_OVER_DISTANCE` | `TOO_FAR` | 「너무 먼 곳이에요」 |
| `CAUSE_LOW_BATTERY` | `LOW_BATTERY` | 「배터리가 부족해요」 |
| `CAUSE_SEARCH_ROUTE` · `CAUSE_SEARCH_TRIP` · 그 밖의(새로 생긴) 값 | `ROUTE_NOT_FOUND` | 「경로를 찾지 못했어요」 |

- 앱 쪽 실패: 미연결 `NOT_CONNECTED` · 응답 없음 `TIMEOUT`(길안내 대기 한도 지남 + 대조 불일치 · 3.2) · 호출 예외 `REQUEST_FAILED`.
- 에뮬레이터 실측(2026-11-06): 현재 위치에서 10 m 인 장소도 `TOO_CLOSE` 없이 안내가 시작됨 · U1 5곳(10 m ~ 382 km) 모두 경로를 찾음 — 대응표는 그대로 두고 오류 행(T10 ~ T13)은 fake 로만 확인(실차 · 다른 내비 판에서 날 수 있음).

### 4.5 서버 테이블 · 시드 (수정: 2026-11-05 서버 사용 팀 결정 반영 — 이 이슈가 만듦)

이 이슈가 `server/` 를 처음 만듦(결정 기록 U39 뒤집음 · #6 D19). server-architecture 「폴더」 · 「도구 묶음」대로(uv · FastAPI · Pydantic v2 · SQLAlchemy async · Alembic · PostgreSQL 17(Docker) · PyJWT · structlog · ruff · mypy --strict · import-linter · pytest · testcontainers). 도메인 패키지 하나(`app/navigation/` — router · service · schemas · models · repository) + `core/`(설정 · 토큰 검증 `current_user` · 오류 코드 · 로그 마스킹) · `db/` · `tools/export_openapi`. LLM · Pleos 호출 없음(`app/llm/` · `app/auth/pleos/` 는 만들지 않음 — 로그인 교환 · 토큰 발급 · 갱신은 #1 · 결정 기록 U28). 첫 Alembic 리비전에 아래 테이블.

| 테이블 | 칸(전부 `comment=`) | 규칙 |
|---|---|---|
| `users` | server-architecture 「데이터」의 칸 그대로(id uuid · pleos_user_id unique · brand · display_name · token_version · created_at) | 표는 이 이슈가 만듦 · 로그인으로 행을 넣는 일 · 토큰 발급은 #1(결정 기록 U27 · U28) · 시험은 시험용 계정 행 + 시험용 비밀로 만든 토큰 |
| `navigation_starts` | id uuid(PK · 서버 생성) · user_id uuid(FK `users.id` `ON DELETE CASCADE`) · place_id varchar(64)(앱 후보 고정 id) · started_at timestamptz(기기가 보낸 시작 시각) · received_at timestamptz(서버가 받은 시각) | 유일: (user_id · place_id · started_at) — 같은 기록을 다시 보내도 한 행(재시도 안전 · 결정 기록 U33) · 색인: place_id · started_at(보관 정리 · 집계) · 좌표 · 이름 · 주소 · VIN 칸 없음 |

- 서버는 후보 장소 목록을 모름 — `place_id` 가 실제 후보인지 확인하지 않음(꼴만 확인).
- 집계 · 조회는 보관 기간(365일) 안 행만(결정 기록 U32 · U33). 시각 허용 폭(미래 5분)도 `Settings` 한 곳.
- 개발 · 시연 시드(U47 추천 기준): **마이그레이션이 아닌** 개발용 시드 명령 하나 — (1) 시드 여행 2 ~ 3건 = 시드 사용자(작성자 표시 이름 · 가짜 pleos_user_id) + 여행 순서대로 시각을 늘린 `navigation_starts` 행 · 여행 이름은 서버에 칸이 없어 넣지 않음(둘러보기 · 공유 업무 4 가 여행 표를 만들 때 함께) (2) debug 시드 계정 1개 + 그 계정의 액세스 토큰 출력(로컬에서만 · 결정 기록 U27). 같은 명령을 다시 돌려도 행이 늘지 않음 · 운영 DB 엔 돌리지 않음 · 값은 U1 답 뒤.

| 422(`VALIDATION_FAILED` · `STARTED_AT_OUT_OF_RANGE`) | 다시 보내도 같은 결과 → 거절(다시 보내지 않음 · 핀은 남음) · 로그에 오류 코드만 |

- 보내기 · 조회는 화면 상태(UiState) · 문구 · 버튼에 영향 없음 · 사용자에게 보이는 보냄 상태 없음 · 주행 중에도 화면 변화 없이 뒤에서 일어남.
- 순서 보장 없음 — 서버는 `startedAt` 으로 시각을 앎.
- 앱 종료 뒤에도 대기 핀은 다시 보냄 · 재부팅 뒤엔 다음 앱 실행 때 다시 예약(결정 기록 U49). 대기 핀 수에 상한을 두지 않음(핀은 여행 기록 · U43 추천 기준).
- 시연 확인 수단 = **debug 빌드 진단 카드에 한 줄**(예: 「안내 건수 A 12 · B 3」 · 서버 조회 · release 엔 없음 · 결정 기록 U41) — 진단 카드 자리는 #6 몫(#6 D9 · D17 · 홈 맨 아래)이라 #6 담당(노희주)과 맞춤 · 맞추지 못하면 시험(T73 ~ T79)만으로 확인. 조회가 실패하면 그 줄은 「안내 건수를 불러오지 못했어요」(debug 전용 · 사용자 문구 아님).
- 서버가 없을 때(개발 · 오프라인): 앱은 정상 동작 · 핀은 대기로 남음 · 시연용 Mock 폴백은 두지 않음(fake 는 시험에만 · U47 추천 기준).
- 고정 해제 · 고정 목록 변경은 핀에 영향 없음 · 핀이 생겨도 고정 목록은 그대로(가 볼 장소에서 자동으로 빠지지 않음).

- 인증: `Authorization: Bearer <우리 서버 액세스 토큰>`(server-architecture 「세션」 — PyJWT HS256 · 클레임 `sub` = `users.id` · `ver` = `token_version` · `exp` · 서버는 서명 · 만료 · `ver` 대조 · 발급은 #1 로그인 · 결정 기록 U28). 두 경로 모두 필요.
- 오류 응답: `{"code": "<UPPER_SNAKE>"}` 하나(한글 문장 없음 · server-architecture 규칙 8). 앱이 코드를 보고 처리(4.6).
- 요청 본문 · 쿼리에 userId 칸 없음(규칙 4) · 정의 밖 칸이 오면 422 — 좌표 · 이름 등이 들어오지 못하게.

| 경로 | 메서드 | 요청 | 성공 응답 | 오류 |
|---|---|---|---|---|
| `/navigation-starts` | POST | 본문 `NavigationStartIn` — `placeId`(문자열 · `^[a-z0-9][a-z0-9-]{0,63}$`) · `startedAt`(date-time · 시간대 필수) | 201 `NavigationStartOut`(새로 받음) · 200 `NavigationStartOut`(같은 계정 · placeId · startedAt 이 이미 있음 — 기존 행 그대로) | 401 `UNAUTHENTICATED`(토큰 없음 · 만료 · 위조 · 지워진 계정) · 403 `CONSENT_REQUIRED`(결정 기록 U31 — #1 의 `consents` 가 생긴 뒤 켬) · 422 `VALIDATION_FAILED`(꼴 위반 · 정의 밖 칸 · 시간대 없음) · 422 `STARTED_AT_OUT_OF_RANGE`(서버 시각 + 5분보다 늦음 · 보관 기간 365일보다 오래됨) |
| `/navigation-starts/stats` | GET | 쿼리 `limit`(정수 1 ~ 100 · 기본 20) · `placeId`(0 ~ 50개 반복 · 꼴은 위와 같음 · 주면 그 장소만) | 200 `NavigationStatsOut` — `items`: [{`placeId` · `startCount`(안내 시작 건수) · `userCount`(서로 다른 계정 수)}] · 정렬 `userCount` 내림 → `startCount` 내림 → `placeId` 오름 · 건수 0인 장소는 없음 · 보관 기간 안 행만 | 401 `UNAUTHENTICATED` · 422 `VALIDATION_FAILED` |

- `NavigationStartOut`: `id`(uuid) · `placeId` · `startedAt` · `receivedAt`. 계정 칸 없음.
- 집계 단위 · 중복 계산: 보관 기간 안 전체 누적 · 같은 (계정 · 장소 · 시각) 재전송은 한 행 · 같은 계정의 반복은 `startCount` 에만 더해짐(결정 기록 U33).
- 서버가 받는 한 건 = 핀 한 건(결정 기록 U45). 요청 칸은 장소 id · 시각뿐 — 핀의 여행 안 순서 · 여행 id 는 이번엔 보내지 않음(U44 추천 기준). 시드 여행은 서버 시드 행으로 같은 집계에 들어감(U47 추천 기준).
