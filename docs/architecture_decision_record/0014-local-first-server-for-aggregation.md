# ADR 0014 — 기기 안 데이터가 원본 · 서버는 로그인 · 추천 집계만(2026-11-05 제안 · 승인 대기)

> **대체됨 — ADR 0015(2026-11-07).** 데이터 원본이 서버 PostgreSQL 로 바뀌었고 좌표도 서버에 둠. 아래는 왜 한때 기기 안을 원본으로 두려 했는지의 기록이며, 지금 규칙이 아님. 승인 전에 전제(일정 · 서버 범위)가 바뀌어 대체됨.

> 원본 규칙: `server-architecture` 「데이터(최소 수집)」 · `android-architecture` 「네트워크 · 세션 · 오프라인」. 이슈 #2 · #4.

## 무엇이 있었나

- 하네스는 「앱 + FastAPI 서버가 로그인 · 대부분의 데이터를 맡음」을 전제로 씀.
- 2026-11-04: 일정(약 1주) 때문에 「서버 없이 시연용으로 가볍게」로 정함(최성호) — 여행 기록 · 공유는 기기 안(11-03 회의 4-1 스냅샷 복제).
- 2026-11-05: spec PR #5 리뷰(giboJK)에서 「다른 사용자에게 장소를 추천하려면 데이터를 서버에 모아야 함」 → 받아들임(최성호). #4 가 `server/` 를 처음 만들고 안내 시작 기록(장소 id · 시각 · 계정)을 받아 장소별 건수를 집계하기로 함.
- 2026-11-05 회의: 팀이 서버(FastAPI)를 쓰기로 함 · 첫 도입은 #4(#6 스펙 D19 · 최성호 확인). 한때 「서버는 계약만 · 앱은 Mock 시연」을 검토했으나(기보님 조언) 팀 결정으로 서버 구현이 #4 안에 들어옴.

## 결정

- 여행 기록 · 공유는 기기 안(Room · DataStore)이 원본 · 서버로 보내지 않음.
- 서버는 여러 사용자 데이터가 있어야 하는 것만 맡음 — 로그인(#1) · 추천 근거 집계(#4).
- 서버로 가는 칸은 기능 스펙의 「최소 수집」 절에 적힌 것만. 좌표 · 기어 · 속도 · VIN · Pleos 토큰은 지금처럼 서버에 없음 — 추천 집계도 장소 id 로만 함.
- 서버로 보낼 기록은 앱의 Room 전송 대기 큐를 거침(보내면 지움 · 실패는 재시도).
- 서버 규칙 · 센서 · CI `server` 잡 · `server-builder` 두 영역 흐름은 그대로 둠(11-04 이슈 본문의 「지움」 요청은 11-05 에 거둠).

## 이유

- 추천은 여러 사용자의 기록을 모아야만 가능 — 기기 안만으로는 근거가 없음.
- 기록 · 공유를 서버로 옮기면 일정 안에 끝낼 수 없고, 수집 항목 · 동의 · 삭제 부담이 커짐(Pleos 심사 「개인정보 · 보안」).
- 좌표 대신 앱 안 장소 id 만 보내면 서버가 사용자의 위치를 모르는 채로 집계할 수 있음.

## 버린 안

| 안 | 버린 이유 |
|---|---|
| 서버 없음 · 서버 규칙 삭제(11-04 안) | 추천 근거를 모을 길이 없음 |
| 기록 · 공유도 서버가 원본 | 일정 · 개인정보 부담 · 회의 4-1(기기 안 스냅샷 복제)과 어긋남 |
| 좌표 그대로 전송 | `server-architecture` 「좌표는 서버에 없음」 위반 · 장소 id 로 충분 |
