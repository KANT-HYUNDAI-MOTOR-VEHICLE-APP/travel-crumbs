# ADR 0014 — 기기 안 데이터가 원본 · 서버는 여러 사용자 데이터가 필요한 곳만(지금은 계약 + Mock)(2026-11-05 제안 · 승인 대기)

> 원본 규칙: `server-architecture` 「데이터(최소 수집)」 · `android-architecture` 「네트워크 · 세션 · 오프라인」. 이슈 #2 · #4.

## 무엇이 있었나

- 하네스는 「앱 + FastAPI 서버가 로그인 · 대부분의 데이터를 맡음」을 전제로 씀.
- 2026-11-04: 일정(약 1주) 때문에 「서버 없이 시연용으로 가볍게」로 정함(최성호) — 여행 기록 · 공유는 기기 안(11-03 회의 4-1 스냅샷 복제).
- 2026-11-05: spec PR #5 리뷰(giboJK)에서 「다른 사용자에게 장소를 추천하려면 데이터를 서버에 모아야 함」 → 받아들임. 이어서 기보님 조언 — 서버 없이 Mock 데이터로 시연하며 기획을 다듬으면 수정 범위가 앱뿐이라 가벼움 → 서버는 지금 만들지 않고 계약만 둠(최성호). 팀 확인 필요.

## 결정

- 여행 기록 · 공유는 기기 안(Room · DataStore)이 원본 · 서버로 보내지 않음.
- 서버는 여러 사용자 데이터가 있어야 하는 것(로그인 · 추천 근거 집계)에만 쓸 수 있음. **지금은 서버를 만들지 않음** — #4 가 보낼 칸(장소 id · 시각 · 계정)과 API 계약만 스펙에 두고, 앱은 Mock 저장소로 시연함. 서버 구현은 후속 이슈.
- 서버로 가는 칸은 기능 스펙의 「최소 수집」 절에 적힌 것만. 좌표 · 기어 · 속도 · VIN · Pleos 토큰은 서버에 없음 — 추천 집계도 장소 id 로만 함.
- 서버로 보낼 기록은 앱 저장소 뒤에 둬서 Mock 구현과 서버 구현을 바꿔 끼울 수 있게 함. 서버를 붙이면 Room 전송 대기 큐를 거침(보내면 지움 · 실패는 재시도).
- 서버 규칙 · 센서 · CI `server` 잡 · `server-builder` 두 영역 흐름은 그대로 둠(서버를 붙일 때 바로 쓰도록 · 11-04 이슈 본문의 「지움」 요청은 11-05 에 거둠).

## 이유

- 추천은 여러 사용자의 기록을 모아야만 가능 — 기기 안만으로는 근거가 없음. 다만 기획이 바뀔 수 있는 지금은 서버를 만들면 데이터 모델 · API 를 두 번 고칠 위험이 큼.
- Mock 으로 시연하며 기획을 다듬으면 수정 범위가 앱뿐이라 시간 · 비용이 적음. 계약을 남겨 두면 나중에 서버를 붙이는 자리가 분명함.
- 기록 · 공유를 서버로 옮기면 일정 안에 끝낼 수 없고, 수집 항목 · 동의 · 삭제 부담이 커짐(Pleos 심사 「개인정보 · 보안」).
- 좌표 대신 앱 안 장소 id 만 보내면 서버가 사용자의 위치를 모르는 채로 집계할 수 있음.

## 버린 안

| 안 | 버린 이유 |
|---|---|
| 서버 없음 · 서버 규칙 삭제(11-04 안) | 추천 근거를 모을 길이 없고, 나중에 서버를 붙일 때 규칙을 되살려야 함 |
| #4 에서 `server/` 까지 구현 | 기획이 바뀌면 데이터 모델 · API 를 두 번 고침 · #1 로그인(계정) 의존 · Docker · 일정 부담 |
| 기록 · 공유도 서버가 원본 | 일정 · 개인정보 부담 · 회의 4-1(기기 안 스냅샷 복제)과 어긋남 |
| 좌표 그대로 전송 | `server-architecture` 「좌표는 서버에 없음」 위반 · 장소 id 로 충분 |
