# ADR 0009 — 사람 기획은 기능 브랜치 `<기능명>/main` 에(2026-10-31 제안)

> 템플릿 주: 하네스 원본 저장소에서 내린 결정을 근거로 옮겨 온 기록. 본문의 이슈 · PR 번호와 날짜는 원본 저장소 것이며, 이 저장소의 새 결정은 다음 번호부터 `0000-template.md` 꼴로 씀.

> 원본 규칙: `team-workflow` 2절 「기능 브랜치에서 기획」 · `app-orchestrator` 0단계 4번 · `docs/spec/README.md`. ADR 0008 의 「사람 기획은 `docs/<기능명>` 브랜치로 이슈보다 먼저 develop 에」를 대신함.

## 결정

- 사람이 GitHub 웹에서 develop 으로부터 `<기능명>/main` 을 만들고, 그 브랜치의 `docs/spec/<기능명>/`(`artifacts/` 밖)에 기획을 직접 커밋함 — 이슈보다 먼저.
- 이슈 「참고」에 `기획: <기능명>/main · docs/spec/<기능명>/`. 에이전트는 0단계에서 이 브랜치를 새로 만들지 않고 그대로 씀. spec · impl 이 이 브랜치에서 따지므로 기획 문서가 작업 트리에 함께 있음.
- `<기능명>/main` 직접 커밋 금지의 예외는 사람 기획 문서 하나. 에이전트는 여전히 직접 커밋 · 푸시 안 함(guard).
- 기획 없이 시작하는 기능은 전처럼 에이전트가 `<기능명>/main` 을 만듦. `docs/<기능명>` 브랜치는 없앰.

## 이유

| 무엇 | 이유 |
|---|---|
| develop 대신 기능 브랜치 | 기능이 없는 기획이 develop 에 먼저 쌓이지 않음. 기획 · 스펙 · 코드가 한 브랜치에서 움직이다 기능이 끝날 때 함께 develop 으로 들어감(사용자 피드백) |
| 사람 직접 커밋 허용 | 기획자는 GitHub 웹의 브랜치 고르기 · 파일 올리기만으로 됨 — PR 단계를 하나 더 두면 git 을 모르는 사람에게 벽 |
| 이슈가 브랜치를 글로 가리킴 | GitHub 이슈는 브랜치에 묶이지 않음. 「Development」 칸의 브랜치 연결은 이름을 GitHub 가 정해 우리 규칙과 안 맞음 |

## 기계로 막는 것

- 없음. 「사람이 올린 기획 문서를 에이전트가 고치지 않음」은 약속(에이전트의 `<기능명>/main` 푸시는 guard 가 이미 막음).
- guard 의 `docs/` 접두 예외는 남음(번호 없는 브랜치라 원래 통과 · 해 없음).
